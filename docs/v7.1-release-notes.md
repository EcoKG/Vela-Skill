# Vela v7.1 — hicoco session hardening

> Status: **release candidate**. All 12 modules landed across 3 phases.
> Release-target branch: `claude/v7.1-hicoco-hardening` → `main`
> Baseline: v7.0.7 (`7296b8c`)
> Version bump: 7.0.7 → **7.1.0**

## Why

Four real pipelines run on the hicoco project against v7.0.7 surfaced 11 quality regressions and ~1000 sub-agent tool_use (executor avg 57.7, verifier 55.2, reviewer 16.1). Every regression maps to a v7.1 module.

Representative failures observed in the hicoco session logs:
- 4 pipelines (T070641/T081421/T083634/T090841) all completed `commit` with `skipped:true` — no `.git/` existed — and the user discovered their work had never been persisted only by reading the final report.
- T081421 verifier fell back to static-only analysis because `npm test | tee` was blocked by VK-08's `|` filter.
- T070641 verifier declared "PARTIAL PASS — dynamic manual" to deflect responsibility for actually running tests.
- T090841 verify FAIL was a stale dev server (node --watch), not a code bug; the user manually `pkill`+restart and overrode with `record pass`.
- T083634 execute 1st-round REJECT 18/25 — CRITICAL DIP violation (`server/index.js` imported `scraper/*` directly). Design decision that should have been caught at plan time.
- T090841 execute 1st-round REJECT 17/25 — `registerSite` conflated book URLs with site root, a plan-level omission the plan-checker passed.
- Artifact directory names truncated mid-syllable to `별도-downloa`, `대상-사이`, `-url-구`.
- 28 sub-agent sessions averaged 28.1 tool_use each, sourceTree-rescanning over and over (Read = 40.3% of all sub-agent tool use).

Full per-module cost + quality counter-analysis in the "Before / after" tables below.

## Phase A — the 4 independent modules

These four ship together because their call graphs don't overlap and
each one carries its own test + reverse-check evidence.

### M1 — commit/branch not-a-git-repo guard
**Before**: hicoco's 4 pipelines all completed `commit` with
`status: "skipped"` because the project had no `.git/`. The user only
realised their work was never persisted when reading the final report.
**After**: `cmdInit`, `cmdBranch`, and `cmdCommit` now detect the
non-git case, emit a multi-line `⛔ BLOCKED` banner to stderr with the
exact recovery steps, and return `status: "blocked"` in the JSON.
`init` additionally embeds a `pipelineWarnings` array and a top-level
`git: { repo, branch, dirty }` snapshot so the PM surfaces the problem
at step 1 instead of step 13.
**Files**: `scripts/cli/vela-engine.js` (cmdInit/cmdBranch/cmdCommit)
**Test**: `scripts/tests/test-commit-not-a-repo.sh` — 18 assertions,
including a git-sandbox reverse-sanity check to prove the banner fires
only in the non-git case.
**Reverse check**: Reverting the engine makes 13/18 assertions fail.

### M5 — slug fs-safe truncation
**Before**: `slugify()` used `.substring(0, 30)` (JS char count).
Korean input produced `별도-downloa`, `대상-사이`, `baseurl` — half-word
artifact directories that also broke shell quoting in downstream
grep/find commands. No side-car for the full request, so truncated
pipelines lost the original prompt.
**After**: new `slugifyEx()` caps at **64 UTF-8 bytes** (not chars),
walks the cut back to the nearest `-` boundary, appends `-trunc` when
truncation triggered, and budgets the suffix in up-front so
post-truncation length is provably ≤ 64. `cmdInit` additionally
drops `request.txt` with the full original prompt when the slug was
truncated, so humans and agents can always recover the intent.
**Files**: `scripts/cli/vela-engine.js` (slugify + slugifyEx + cmdInit)
**Test**: `scripts/tests/test-slug-truncate.sh` — 15 assertions
including 4 unit cases (short/long-ko/long-mix/200-char) and an
end-to-end cmdInit integration check.
**Reverse check**: Reverting makes 10/15 assertions fail. Pre-v7.1
output confirmed byte length 70 and mid-syllable cut `-url-구`,
matching the exact hicoco bug.

### M8 — advance command (record + transition one-shot)
**Before**: hicoco PM emitted 146 top-level Bash calls, the largest
single pattern being `record pass` followed by `transition` on every
successful step. After transition the PM often called `state` to
figure out which agent to spawn next — three CLI calls per happy step.
**After**: new `advance [pass|fail|reject]` command. `advance pass`
records the verdict + advances atomically, writes `pipeline-state.json`
once, and returns `{previousStep, currentStep, nextStep, revision,
circuitOpen, nextAction}`. `nextAction` is a one-line hint like
`"spawn vela-executor then vela-reviewer"` so the PM can skip the
extra `state` call. `record` and `transition` are fully preserved for
back-compat.
**Files**: `scripts/cli/vela-engine.js` (cmdAdvance + applyVerdict
helper + nextActionHint lookup table)
**Test**: `scripts/tests/test-engine-advance.sh` — 18 assertions
covering pass/fail/reject/default/invalid verdicts + legacy
record/transition preservation.
**Reverse check**: Reverting makes 14/18 assertions fail (the 4 that
still pass are Phase 5/6 — legacy `record`/`transition` / unknown
command branch — which v7.0.7 already supported).

### M12 — CLAUDE.md cd-rule injection on upgrade
**Before**: v7.0.7 added the "Bash tool — never use bare `cd`" section
to `install()`'s CLAUDE.md template, but only for first-time
initialisation. Pre-v7.0.7 projects like hicoco have a CLAUDE.md that
`upgrade()` deliberately skips (to preserve user customisation), so
they never get the rule and keep stepping on the subshell-cd footgun
on every session.
**After**: `upgrade()` reads the existing CLAUDE.md, checks for the
marker `Bash tool — never use bare \`cd\``, and appends the section
if absent. Idempotent — re-running `upgrade` after the first injection
is a no-op. Files with the marker already present are untouched
(size unchanged).
**Files**: `scripts/install.js` (upgrade)
**Test**: `scripts/tests/test-claudemd-cd-rule-injection.sh` — 10
assertions across 3 scenarios: no CLAUDE.md at all, existing without
marker, existing with marker.
**Reverse check**: Reverting makes 6/10 assertions fail.

## Phase B — the 7 dependent modules

Phase B modules have ordering constraints — M2 must land before M3 (smoke test Bash), M4 before M11 (scope relies on Guardrails), M7 before M9/M10 (cost measurements depend on Context Pack).

### M2 — Gate Keeper verify bash safelist
**Before**: hicoco T081421 verifier tried `npm test | tee` and was blocked by VK-08's `|` filter, falling back to static-only analysis and passing the pipeline without exercising any runtime code. Root cause: VK-08's chain-operator block was a blunt instrument.
**After**: when `pipelineState.current_step === "verify"`, vela-gate-keeper.js matches the command against a safelist of known test/lint runners (npm test, vitest, pytest, go test, cargo test, node --check, etc.) that *explicitly* permits pipes. Malicious piped commands (`rm -rf / | echo`, `git reset --hard | tee`) still block because they don't match the safelist. Project extras live at `.vela/guidelines/verify-commands.txt`.
**Files**: `scripts/hooks/vela-gate-keeper.js` (VERIFY_SAFELIST_PATTERNS, loadVerifyExtras, isVerifyStepSafe), `scripts/agents/vela-verifier.md`
**Test**: `scripts/tests/test-verify-bash-allowed.sh` — 14 assertions. Reverse-check: 5/14 fail.

### M3 — Verifier Phase 0/3/4.5 expansion
**Before**: verifier's 5-step procedure was too loose — PARTIAL PASS was a legal verdict and Phase 0 (live processes) wasn't a concept. hicoco T070641 used PARTIAL PASS to defer dynamic verification to the user. T090841 was a stale `node --watch` server that the user had to kill+restart manually.
**After**: 7-phase structure (0: live-process recovery, 1: static, 2: unit tests, 3: smoke test, 4A: ref integrity + 4B: Forbidden imports, 4.5: out-of-scope, 5: writeup). Phase 0 consumes `.vela/guidelines/live-processes.json` to kill+restart and poll readyPath before tests. Phase 3 runs `.vela/guidelines/smoke-test.sh` or `npm run test:smoke` or logs an explicit "WARNING: no smoke test defined" and passes as PASS (**not** PARTIAL). "PARTIAL PASS" is explicitly banned by the prompt. Fallback on Bash-blocked: verifier must set `fallback: true` and emit stderr warning, **not** silently static-only.
**Files**: `scripts/agents/vela-verifier.md`, `templates/guidelines/live-processes.json`, `templates/guidelines/smoke-test.sh.example`
**Test**: `scripts/tests/test-verifier-smoke.sh` — 26 assertions. Reverse-check: 20/27 fail.

### M4 — Architecture Guardrails + plan-checker sanity
**Before**: plan-checker only verified "are the 3 required sections present and ≥ 200 bytes". Content quality wasn't checked, so T083634 (DIP violation) and T090841 (registerSite URL conflation) both got through plan-check and were caught expensively by the reviewer during execute.
**After**: 4 required plan.md sections (added `## Architecture Guardrails` with Allowed/Forbidden/Injection subsections), Phase 3 design-sanity heuristics with three sub-checks: (a) Guardrails concreteness, (b) ClassSpec domain-value `format:`/`must be` constraints, (c) Test Strategy edge-case cardinality ≥ 2. Phase 3 fail = whole plan FAIL. verifier.md gains Phase 4B which greps the diff for plan-declared Forbidden imports and FAILs the pipeline on match. `templates/plan-templates/quick.md` ships a fully-populated example.
**Files**: `scripts/agents/vela-planner.md`, `scripts/agents/vela-plan-checker.md`, `scripts/agents/vela-verifier.md`, `templates/plan-templates/quick.md`
**Tests**: `test-plan-checker-sanity.sh` (27 assertions, reverse 20/27 fail), `test-architecture-guardrails.sh` (8 assertions end-to-end grep demo, reverse 4/8 fail)

### M11 — Researcher targeted scope enforcement
**Before**: hicoco researchers averaged 12 tool_use per session even when `targets.primary[]` was just 2 files. They read `server/index.js`, `client/src/App.jsx`, etc. — unrelated but easy to discover via a broad Glob. No runtime enforcement.
**After**: vela-researcher.md targeted mode strictly allows Read only on `targets.primary[]` ∪ `blast_radius[]` ∪ `tests[]` plus a small metadata allowlist (`package.json`, `README.md`, `.vela/*`, etc.). vela-gate-keeper.js enforces the same in the hook layer: when `current_step === "research"` and confidence is high/medium, out-of-scope Read calls exit 2. Legacy (no targets.json or low confidence) falls through to the old exploratory path.
**Target**: researcher avg 12 → ≤ 8 tool_use.
**Files**: `scripts/agents/vela-researcher.md`, `scripts/hooks/vela-gate-keeper.js` (isResearcherReadOutOfScope)
**Test**: `test-researcher-targeted-scope.sh` — 16 assertions, reverse 6/16 fail.

### M7 — Context Pack (researcher → executor/verifier)
**Before**: hicoco sub-agents re-scanned the project tree every pipeline. Read = 40.3% of 787 sub-agent tool_use. researcher had already done the work but the findings lived in prose-only `research.md`, not in a machine-readable shape.
**After**: new required researcher deliverable `context-pack.json` with schema `{version, sourceTree, entryPoints, testDirs, conventions, relatedFilesForRequest}`. executor.md reads it first and is BANNED from Glob/Grep-scanning the project afterwards. verifier.md reads `conventions.testRunner` and `testDirs[]` to decide Phase 2 commands without filesystem discovery. cmdState() exposes `contextPackPath` so the PM can inject the path into Agent spawns without filesystem checks.
**Target**: executor avg 57.7 → ≤ 35, verifier 55.2 → ≤ 30, sub-agent Read 40% → ≤ 25%.
**Files**: `scripts/agents/vela-researcher.md`, `scripts/agents/vela-executor.md`, `scripts/agents/vela-verifier.md`, `scripts/cli/vela-engine.js` (cmdState)
**Test**: `test-context-pack.sh` — 18 assertions.

### M9 — Role budgets
**Before**: hicoco executor maxed at 88 tool_use in a single session; verifier maxed at 92. No budget concept existed, so nobody flagged the outliers until session-end review.
**After**: `templates/role-budgets.json` defines per-scale budgets (small/medium/large/surgical/ralph/hotfix) for executor/verifier/reviewer. Numbers derived from hicoco telemetry with ~40% slack: `large = {80, 60, 25}`, `small = {15, 15, 10}`, etc. Agent prompts each document the rule: exceeding is non-fatal, the agent drops `budget-exceeded.json` in artifactDir and notes it in the final writeup. vela-stop.js `rollupToolUsage()` aggregates markers into `tool-usage.json` for /vela:analyze.
**Files**: `templates/role-budgets.json`, `scripts/agents/vela-executor.md`, `scripts/agents/vela-verifier.md`, `scripts/agents/vela-reviewer.md`, `scripts/hooks/vela-stop.js`
**Test**: `test-role-budgets.sh` — 24 assertions.

### M10 — File read cache hook
**Before**: Context Pack (M7) is the defense, but without measurement we can't tell whether it's working. No instrumentation existed to count duplicate Reads across sub-agent sessions.
**After**: new `vela-file-read-cache.js` PreToolUse hook logs every Read call to `<artifactDir>/read-cache.jsonl` with `{ts, agent, file, sha16}`. Emits a stderr warning on the 4th identical (agent, file, sha) read per pipeline. Purely observational (always exits 0, never blocks). No-op outside Vela. `vela-stop.js` rolls the JSONL into `tool-usage.json.duplicateReads` for /vela:analyze.
**Files**: `scripts/hooks/vela-file-read-cache.js` (new), `scripts/hooks/vela-stop.js`, `scripts/install.js` (FILE_MANIFEST + registerGlobalHooks)
**Test**: `test-file-read-cache.sh` — 19 assertions.

## Phase C — M6 + release wrap

### M6 — Engine doctor + session-start wire-in
**Before**: hicoco's initial session (`ff03bb16`) had the user instructing "vela install.js 로 환경구성부터 똑바로 해" because the PM didn't detect `.vela/` was incomplete. PM limped along until the first Agent spawn died with "file not found".
**After**: new `cmdDoctor()` CLI command that walks every Vela-managed file (core dirs, cli/engine, pipeline.json parse, config.json parse, agent manifest, v7.1 templates+hooks) and returns `{ok, checks[], missing[], recovery}`. vela.md session-start flow gains step 1.5: run `doctor` after the walk-up `cd` and before `state`. On `ok:false`, the PM asks the user (via AskUserQuestion) to run `node .vela/install.js validate` and only proceeds on success. install.js upgrade() now also ensures `.vela/artifacts/` exists so first-time doctor calls on fresh installs pass.
**Files**: `scripts/cli/vela-engine.js` (cmdDoctor), `scripts/agents/vela.md` (1.5단계), `scripts/install.js` (artifacts dir creation on upgrade)
**Test**: `test-engine-doctor.sh` — 19 assertions, reverse 9/19 fail.

```bash
curl -fsSL https://raw.githubusercontent.com/EcoKG/Vela-Skill/main/update.sh | bash
```

Existing projects pick up the 4 new templates (`role-budgets.json`, `plan-templates/quick.md`, `guidelines/live-processes.json`, `guidelines/smoke-test.sh.example`), the new file-read-cache PreToolUse hook, and the CLAUDE.md cd-rule injection automatically via `upgrade()`.
