# Vela v7.1 — hicoco session hardening

**Status**: planning → Phase A in progress
**Branch**: `claude/v7.1-hicoco-hardening`
**Baseline**: `7296b8c` (v7.0.7)

## Context

Analysis of 4 hicoco pipelines (T070641/T081421/T083634/T090841) in `~/.claude/projects/-home-starlyn-hicoco/` surfaced 11 quality regressions and a ~1000 tool_use cost bloat, with `executor` averaging 57.7 calls and `verifier` 55.2 per pipeline. Root causes traced back to:

- `commit` step silently `SKIPPED` in non-git projects → user work never persisted
- `verify` step allowed PARTIAL PASS and static-only fallback when Bash was blocked
- `plan-check` checked section presence/length only — architectural defects reached `execute` and were caught late by `reviewer`
- slug truncation corrupted artifact directory names mid-word
- researcher/executor/verifier re-scanned the repo from scratch every pipeline (Read 40.3% of all sub-agent tool_use)
- `install.js upgrade()` never injected the `Bash — no bare cd` rule into pre-existing `CLAUDE.md` files

v7.1 ships 12 modules addressing these exact signals. Reported before/after metrics land in `docs/v7.1-release-notes.md`.

## Dependency graph

```
                 ┌──────────────────────────── independent ────────────────────────────┐
                 │                                                                     │
   Phase A:     M1 commit guard    M5 slug fs-safe    M8 advance cmd    M12 CLAUDE.md inject
                                                                                        │

                 │                                                          │           │
   Phase B:    M2 gate-keeper verify bash ─► M3 verifier Phase 0/3/5        │           │
               M4 guardrails sanity     ─► M11 researcher scope             │           │
               M7 context pack          ─► M9 role budgets  + M10 read cache           │
                                                                                        │
                 ┌──────────────── runs last (depends on all above) ────────────┐      │
                 │                                                                │     │
   Phase C:    M6 engine doctor   +   CI wire-in (12 new tests)   +   v7.1 release bump
```

Why this order:

- **Phase A** modules touch orthogonal files and share no call graph — safe to land in any sub-order and each carries its own test.
- **M2 must precede M3** because verifier Phase 3 (smoke tests) calls `bash test:smoke` which requires gate-keeper to allow project-defined test commands.
- **M4 must precede M11** because researcher targeted-scope enforcement reads Architecture Guardrails as its authority for which files are in-scope.
- **M7 (Context Pack) must precede M9/M10** because the budget reductions and file-read cache measure the Context Pack's effect; landing them in reverse would show false "no regression" results because the baseline is still high.
- **M6 doctor runs last** because it validates every artifact the other modules create (role-budgets.json, plan-templates/quick.md, etc.).
